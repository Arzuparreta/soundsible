# Soundsible on TV

**Proposal for review.** The first release should let someone open their station on a living-room TV, choose music with six buttons and hear it on that TV. A second person with an authorized phone can select the TV and control the same queue. The phone can then leave the room. Playback and browsing must still work with the remote.

## From the sofa

- **Arrival.** Open the station's explicit `/tv/` URL and bookmark it. Show that address from the existing web player's device area for first-time setup. A phone scanning a QR on a TV can authorize the TV only after the TV has reached the correct station. For an installed launcher later, remember the last station, offer Change station and keep the selector reachable after a connection failure.
- **Returning listener.** Home focuses Resume when a playable session exists. One OK resumes it locally. Otherwise focus the first playable recent item, then a library entry if history is empty. With an empty library show the existing search path. Opening the app, moving focus or reconnecting must never start audio. Show the current account and provide Sign out on a shared TV.
- **Browse.** Use Home, Search and Library as primary destinations. Home shows recent listening and saved collections. Album and playlist cards open details with Play and the track list. Selecting a track starts the collection at that track. Search uses the system text input and a submit action, preserves the query on Back and supports empty, loading, no results and retry states. Keep a reachable Now Playing entry whenever a session exists. Defer recommendation ranking, library editing and account administration.
- **Listen.** Now Playing shows artwork, title, artist, elapsed time, Play/Pause, Previous, Next and Queue. On an explicitly focused seek control, Left/Right preview the position, OK commits and Back cancels. In Queue, identify the current track and let OK on an upcoming track select it by queue ID. Browsing and opening the queue preserve audio. A user-selected dim view hides bright static artwork and controls. The first directional key restores the view and focus without also navigating. Keep system volume, Home and power with the platform.
- **Focus.** Left/Right move along a shelf, Up/Down move to the adjacent shelf at the closest visible column. Left at the first card opens the rail. Returning from the rail restores the last card. Clamp at other edges. List movement scrolls just enough to reveal the whole target. Use native focusable elements, stable IDs and one active target. Repeated arrow presses may navigate, held OK activates once. Pointer movement takes over on deliberate movement. Switching back to arrows starts at the last active item. An artwork load, remote track change or late search response cannot steal focus.
- **Back.** Close keyboard, dialog or queue overlay first, then pop the route and restore its scroll position and focused item. If the item disappeared, choose the nearest surviving sibling or section entry. At root, let the host leave. Provide an on-screen Back action on detail views for browsers that consume the hardware key. Trap focus only in the topmost modal.
- **Readability.** At a 1920 × 1080 design viewport, start with 32 px body text, 44 px titles, 64 px minimum control height and 5% margins around essential actions. Scale for the actual CSS viewport. Use a solid focus outline plus a surface change visible over both light and dark artwork. Distinguish focus, selected and playing. Support reduced motion, localized labels, long titles, missing artwork and system keyboard input. Check from three metres in daylight and in a dark room. These dimensions are starting points for that test. [Android adaptive TV guidance](https://developer.android.com/develop/adaptive-apps/guides/tv/build-adaptive-apps-for-tv)

## Architecture and distribution decision

Add a SolidJS entry under `ui_web/src/tv/`. Its responsibilities are the TV shell, route and overlay stack, navigation groups, focus restoration and platform input normalization. Use hash routes so deep views reload through one HTML entry. Reuse the existing account, catalog, collection, queue, audio, session and remote command implementations. A widened desktop layout would inherit pointer menus, keyboard shortcuts and desktop information density. A separate React/Enact or canvas renderer adds a second component and accessibility stack. Reconsider a specialized renderer only if profiling on a target set shows that a bounded DOM cannot meet the focus budget.

1. Add `ui_web/tv.html` as a second Vite input. Serve `/tv` with a permanent redirect to `/tv/`, and serve the entry same-origin with revalidation disabled by using `Cache-Control: no-store`. Reuse hashed assets under `/player/assets/` and existing API, media and Socket.IO origins. Keep the TV document outside the player service-worker scope. Include the new HTML in source revision and freshness checks, require both outputs in new distributions, handle an older external dist with a clear unavailable response, and exercise packaged and source installs. Inspect generated entry imports, startup plugin, payload manifest and desktop payload budgets. A second entry can change shared chunks.
2. Start the signed-in client once per account via the store lifecycle in `ui_web/src/stores/index.ts`. Parameterize the desktop shortcut binding in `stores/runtime.ts` while retaining the real gesture unlock handler. Use existing PlayerActions for local UI and receiver execution. Own audio above routes. Release listeners, socket, account data and playback on logout. On visibility return, reconcile the real media state, queue and connection before painting Playing. Recover from process death into a resumable, paused session. Qualify background playback separately.
3. Register as device type web, with explicit TV form factor and a renameable room/device label. Extend normalization in `shared/playback_state.py`, web identity/types, device rows and the [remote contract](../remote/CONTRACT.md). Preserve older clients' generic-device fallback. Reuse per-device identity, per-load instance ID and receiver ownership. Start on this TV. Phone control requires explicit selection and uses the existing state events, capability advertisement and command acknowledgments. If autoplay is blocked, show “Press OK to play” and publish the actual state. A transfer may release the source only after the destination starts. Restrict advertised commands to tested capabilities, including DJ and software volume.
4. Target the LG browser first. Start by probing a webOS 24-class Chromium 108 engine and a current set. Select the oldest supported model from real results. Check emitted JS, CSS, cookies, storage, Web Audio, media codecs, streaming/seek and socket reconnection on LAN HTTP and on the station's HTTPS origin. If lowering the compilation target becomes necessary, measure a TV-specific build before changing the desktop target. A small static boot message should survive failure to parse the app.
5. A later LG hosted launcher can save the station URL and load the same interface. Compare it on-device with a packaged client if origin restrictions, remote events, session persistence or store rules block that route. Samsung Tizen needs its own input/lifecycle adapter and qualification. Android/Fire TV native shells merit a separate decision where browser availability or background audio is inadequate. Casting is a complementary phone-driven entry. It cannot satisfy the independent browse-and-play journey.

## Sign-in and account boundaries

The current signed-in display creates a code and the **claiming device** gets the session cookie in `shared/api/routes/pairing.py`. Reuse that today by letting the user display a code on an authorized device and enter it on the TV with the pairing sheet open. Preserve existing station login and trusted-network rules. Acknowledge expiry, allow retry, and retain the selected station. Confirm the existing route's account and permission requirements on a non-admin account before enabling this option.

For the preferred TV-displays-code journey, implement a distinct device authorization flow in the station. The TV creates a short-lived pending request and retains a high-entropy private redemption handle. Show a public short code and a QR linking to the station's approval page. The phone signs in there, verifies the matching code and room, then explicitly approves its own account. The TV redeems with the private handle and receives a normal revocable session cookie. Persist hashed handles, expiry, status and approving account. Rate-limit creation, attempts and redemption. Enforce same-origin authenticated approval with CSRF protection. Consume approval and create the session atomically. Keep credentials out of QR payloads, URLs and logs. Cancel on dismissal and expire abandoned requests. Test two simultaneous TVs, wrong codes, denial, expiry, repeated redemption, concurrent approval, account switching and revocation during playback. Use a bounded, backing-off status check solely during sign-in. Device control stays event-driven.

For the implementation PR, run API and store tests, the full web unit suite and all four existing Playwright profiles, followed by a TV viewport suite covering key sequences, long lists, dialogs, restore after Back, pointer handoff and repeated keys. Test the production entry served by Flask as well as the Vite test fixture. Check boot payload against the existing desktop budget. Attach a short PR recording of the first-play journey and focus restoration.

**Proposed hardware acceptance targets.** With a warm station on LAN and a local playable track, record cold launch to first focus, OK to audible output and keydown to painted focus. Aim for first focus within 3 s, audio within 2 s and p95 focus response within 100 ms across 100 directional presses. Record device, library size, sample count and cache state. Measure external-provider start separately. Exercise a long playlist for ten minutes, change tracks, open/close Queue and confirm bounded rendered rows, stable focus and continuous audio. Repeat with missing artwork, a failed stream, network loss, TV standby, a revoked account and a clean profile. Use a real remote and audible output for the pass decision. Automated Chromium tests cover interaction regressions.

**Decisions for review.** Recommend LG browser first, full independent listening from the first release, and phone-approved QR sign-in alongside the existing code-entry route. Prioritize these over lyrics, profile switching, TV-side DJ editing and store packaging. Revisit launch distribution immediately if entering or reopening the station URL proves the main barrier in the sofa test. Keep secondary platforms listed as candidates until each completes the same journey.
