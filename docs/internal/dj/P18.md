# P18. Tempo shared between the two songs

User decision (2026-10-26, implemented on 2026-11-05): split the
tempo change between the two songs during the mix, each one within
8 % of one deck, and return gradually. Before, only the incoming song moved, with
8 % as the limit; now the limit is 8 % per deck and the mixable difference
reaches approximately 16 %.

## Criterion

`playback_rate` keeps its meaning: seconds of the incoming song per second
of the outgoing song, the ratio that keeps the phase. Cues, coverage, arrival at the
drop and `rate_fits` still work in file time and do not change.

`timing.deck_rates(r)` chooses the speeds of the two decks:
`s_out = 2 / (1 + r)` and `s_in = r · s_out`. Both move away from normal
speed by `|1 − r| / (1 + r)`, the smallest possible maximum change of the two (there is
no other pair that keeps `r` while changing the deck that changes most by less). It is a
mathematical criterion, without taste constants.

- 120 ↔ 132 BPM: they meet at 125.71 BPM, 4.76 % each deck (the incoming song
  alone would need 9.1 %).
- 120 ↔ 140 BPM: 129.23 BPM at 1:1, 7.69 % each deck. **1:1 goes first
  whenever it fits** (user decision, 2026-11-05), even though 3:4 would change
  one point less (6.67 %): 3:4 only keeps one out of every three beats together.
  120 ↔ 141 no longer fits at 1:1 (8.05 %) and uses 3:4.
- Among the other cycles, the ratio is ordered by that maximum change
  (`timing.deviation`); with old clients it is still `|1 − r|`. Within
  8 % of a single deck no other cycle fits next to 1:1, so their
  plans do not change.
- Each deck stays at most one 0.25 % step from the limit
  (`MAX_STRETCH − RATE_STEP` = 7.75 %): the minimum step with which the
  players correct the phase must fit in both directions.
- The tempo score measures the change made by the deck that changes most. With
  new clients, a 120 ↔ 126 pair goes from `filter_blend` to `bass_swap`.

## Contract

Only for clients that send `X-Soundsible-Dj-Rates: split` (web and Android of
this version). `session.scoped` sets `timing.split_rates` during the request;
any other client receives exactly the previous plans (test
`test_old_clients_receive_exactly_the_plans_they_were_built_for` and the 552
previous DJ tests unchanged).

- `out_playback_rate`: speed of the outgoing song during the overlap.
- `out_rate_ramp`: `{lead_seconds: 15, seconds: 8}`. The outgoing song reaches its
  speed between `out_cue − 15` and `out_cue − 7` seconds of its file, with
  the same 8 s ramp that the return already used. The 7 s cover the ≤ 4 s of
  silent pre-start and the second that Android waits with stable speed
  before arming the mix, at 1.0775× at most.
- Without room for the ramp (`out_cue < 15`): only the incoming song moves if it fits
  alone in the 7.75 %; otherwise there is no beatmatch.

## Execution

Web (`audio/mixer.ts`) and Android (`ProgramDjSession.prepareOutgoing`):

- The ramp of the outgoing song follows the position of its file, with zero-slope start and
  end (smoothstep) in steps of 0.25 %: a pause
  freezes it and a seek repositions it. It starts from the speed that the
  deck currently has (a previous return can still be in progress) and is never steeper
  than the complete ramp from 1×; if it does not fit, only the incoming song moves or
  a fade without a phase promise is done (`mix.execution_fallback`,
  `rate_ramp_late`).
- The incoming song starts at `playback_rate × current speed of the outgoing track`.
  On the web the phase is measured in file time, so it is kept whatever
  the speed of the outgoing song; corrections never take a deck outside
  ±8 %. Android schedules the mix with the output clock and arms it only
  when the outgoing song has been at its final speed for 1 s.
- The fade lasts `overlap / s_out` seconds of output: it ends where the plan
  put it in the file of the outgoing song.
- At the end, the incoming song returns to its tempo in 8 s; the return is now
  also smooth and, on the web, stops during pauses. If the mix is
  cancelled, fails or is released, the outgoing song returns to 1× in the same way.
- The web also corrects the phase during the silent pre-start (see
  measurements): before, it only did so when the incoming song was already playing.
- A speed outside the range is no longer silently clipped to 0.92/1.08
  while keeping the beatmatch promise: it is a structural fade.

## Measurements

**Browser** (`tests/browser/dj-shared-tempo.spec.ts`). Clicks of 4 ms at
1 kHz (outgoing) and 3 kHz (incoming) go through the real mixer, the
renderer stretching, the graph and the limiter. The program output is recorded
as the Live listeners receive it
(`acquireBroadcastCapture`) and the beats that sound are measured.

- Audible tempo: before the ramp the outgoing song plays at 0.500 s per beat;
  during the mix both at 0.4773 s, the shared tempo.
- Mean absolute phase error during the mix, Chromium, local
  repetitions on 2026-11-05:

  | Case | First 2 beats | Whole mix |
  | --- | --- | --- |
  | `main`, only the incoming song (120 → 126) | 11–32 ms | 12–17 ms |
  | This branch, only the incoming song, without correction in the pre-start | 33–38 ms | 13–18 ms |
  | This branch, only the incoming song | 12–25 ms | 9–16 ms |
  | This branch, shared tempo (120 ↔ 132) | 6–29 ms | 8–17 ms |

- Chromium stretching by itself moves each beat of a deck: the
  outgoing song alone at 1.0476×, without a mix, has between −17 and +15 ms of variation
  between consecutive beats. The 5 ms of the planner are met on the
  playback clocks, not beat by beat in the audio of this renderer.
  The test requires the shared tempo and a mean error < 30 ms; a deck at an
  unaccounted speed would drift 270 ms in this mix.
- The initial error (40–50 ms in `main`) comes from the latency of `play()` or from
  a seek in the incoming song. Without correcting it in the pre-start, a pair close to the
  limit (7.69 %) would only have a 0.31 % margin in that direction and would take
  about 15 s to close it.
- WebKit in the Playwright container (GStreamer, Linux) drops any
  element to `readyState = 2` as soon as `playbackRate ≠ 1` and does not recover it
  when returning to 1×; the mixer therefore never admits a stretched incoming song. The
  test is skipped there. The iPhone WebKit keeps `readyState = 4`
  during the ramps (P15 trace).

**Android** (`DjSharedTempoTest`, emulator API 36): the native service
mixes equivalent click tracks (fixture `/__fixture/dj-shared-tempo`) and
its output PCM is measured (`NativeProgramOutput`). The native planner
sends the `split` header in all its route requests.

| Case | Audible tempo in the mix | Signed error of the incoming song |
| --- | --- | --- |
| Only the incoming song (120 → 126), as before | 0.500 s | constant in each run: +6, +7 and +15 ms in three starts |
| Shared tempo (120 ↔ 132) | 0.4773 s in both | +6 to +23 ms; mean 11–19 ms in three starts |

- Android does not correct the phase during the mix: it schedules the start with the
  output clock. Its error is almost constant, without the beat-to-beat variation
  of the Chromium stretcher.
- **The incoming song plays between 6 and 15 ms late already with a single speed**: this is the
  pending P2 measurement on Android. Shared tempo does not introduce it. The
  cause is not identified; the candidate is the latency of the ExoPlayer
  stretcher (Sonic) on the incoming song, which is partly compensated when both decks are stretched.
  It is not corrected here: compensating a number without a known
  cause would be calibration.
- The test found a bug before publishing: `EngineConnection` only
  lets through a closed list of headers and rejected the new one, so
  the native planner never obtained a route (DJ `unavailable`).

## Initial web load

The mixer grows by about 850 bytes gzip. The user raises the limit of the authenticated
load in `check-payload.mjs` from 85 % to 86 % of the #284 reference
(2026-11-05). Moving the code to a deferred module only saved 150 bytes:
almost all of the change is in the phase and speed that any mix uses.
