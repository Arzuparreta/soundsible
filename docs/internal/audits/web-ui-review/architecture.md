# Web UI foundation review — independent code architecture angle

> Imported from an independent review of `00fd7d0a` (2026-11-16). Only links were rewritten. Scripts, traces, screenshots and data files it names stayed in the reviewer's working directory and are not part of the repository. Read [the handoff](../WEB_UI_REVIEW_HANDOFF.md) first: it records which findings were verified, refuted or reclassified afterwards.

Reviewed revision: `00fd7d0ae3b0d48e610d8643d6e6614e5ece63ed`, 2026-11-16.

## Summary verdict

1. Keep Solid, TypeScript, Vite, HashRouter and CSS Modules; the code does not establish a framework limitation.
2. The current architecture nevertheless fails to enforce bounded rendering and narrow invalidation consistently.
3. Virtualizing DOM does not bound saved-state scans, synchronous search, full snapshots or hidden-view computations.
4. Unvirtualized collection surfaces and divergent list implementations make performance depend on where the same music is opened.
5. A reproduced collection/catalog invalidation fault also explains a concrete class of cross-view inconsistency.
6. Keep the engine's canonical musical identities and separate queue-occurrence identities throughout the UI.
7. Target domain-owned keyed state, shared query projections, one list/scroll infrastructure and platform-neutral presentation components.
8. Preserve native scrolling; centralize geometry, restoration and gesture arbitration instead of adding more local timing repairs.
9. Make visual patterns and material fallbacks component contracts, supported by rendered cross-engine evidence.
10. Migrate incrementally with behavioral gates and production traces; no evidence here justifies another whole-framework rewrite or promises a particular frame rate.

## Findings, ordered by likely impact on the reported problem

### 1. Mounting a virtual row can still scan the entire saved collection

**Read:** [stores/identity.ts:254](../../../../ui_web/src/stores/identity.ts#L254) calls `savedEntryForIdentity(state.saved, ...)`; [lib/saved.ts:14](../../../../ui_web/src/lib/saved.ts#L14) uses `find` for canonical item identity and full `filter` scans for compatibility identities. [FavouriteButton.tsx:28](../../../../ui_web/src/components/FavouriteButton.tsx#L28) and [MusicListRow.tsx:8](../../../../ui_web/src/components/MusicListRow.tsx#L8) call these selectors. An index already exists at [stores/identity.ts:69](../../../../ui_web/src/stores/identity.ts#L69), but this lookup does not use it. Optimistic favourite changes replace the saved array at [stores/collection.ts:82](../../../../ui_web/src/stores/collection.ts#L82).

**Measured:** `node --conditions=browser <output>/probe.mjs`, Node v26.13.1, installed project Solid runtime, synthetic saved entries, 30 mounted-lookup memos. `probe-rerun.json` records:

| Saved entries | Lookups near the array's end | Item-ID property reads during initial lookup | Memos rerun by an unrelated optimistic favourite | Memos rerun by a clock write |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 30 | 29,565 | 30 | 0 |
| 10,000 | 30 | 299,565 | 30 | 0 |

An unrelated leaf-path favourite write caused zero lookup-memo reruns in both cases. These are operation counts, deliberately unfavorable lookup positions, not application timings or representative library distributions. Some surfaces invoke more than one ownership selector per row; the experiment does not count the whole row.

**Consequence inferred from code:** Fast scrolling continually mounts new rows, so a bounded DOM can still perform work proportional to saved-library size for each newly mounted row. A mark change can additionally rerun every mounted lookup. This is directly relevant to song-list scrolling even without any fancy visual effects. It is a misuse of data access boundaries, not evidence that Solid rerenders the whole app.

### 2. Rendering is bounded on some routes and unbounded on adjacent surfaces

**Read:** [AlbumGrid.tsx:17](../../../../ui_web/src/components/AlbumGrid.tsx#L17) and [ArtistGrid.tsx:13](../../../../ui_web/src/components/ArtistGrid.tsx#L13) render the complete supplied collection with `For`. The player browser's album view also renders every album at [NowPlayingBrowser.tsx:919](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L919). Its local-search view renders every result at [NowPlayingBrowser.tsx:1040](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L1040), while the route-level [LibrarySearchResults.tsx:82](../../../../ui_web/src/components/LibrarySearchResults.tsx#L82) virtualizes results.

**Read:** [lib/librarySearch.ts:38](../../../../ui_web/src/lib/librarySearch.ts#L38) normalizes several fields for every track and sorts matches on each query. [Library.tsx:93](../../../../ui_web/src/routes/Library.tsx#L93) runs it directly in a memo; [NowPlayingBrowser.tsx:213](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L213) derives another library/sort/search projection. It is not a clock dependency, but it remains synchronous main-thread work during typing and collection changes.

**Read:** [SearchDiscoveryView.tsx:65](../../../../ui_web/src/components/SearchDiscoveryView.tsx#L65) bounds the ordinary song preview, but expanded songs and entity rails/grids render their full supplied arrays at lines 65 and 115. A short feed is reasonable; the view itself defines no large-collection rendering policy.

**Consequence inferred from code:** Opening Albums, Artists, expanded results or player-local search can create a substantially larger DOM/reactive graph than opening Songs. Lazy images do not virtualize that graph. A professional target must cover collection grids, search, editing and rails as well as the main song list. Merely adjusting the existing virtualizer cannot fix the unvirtualized paths.

### 3. Broad server refreshes and presentation metadata retain expensive invalidation paths

**Read:** The current canonical path at [stores/library.ts:159](../../../../ui_web/src/stores/library.ts#L159) requests `getCollection(collectionRevision)`. An unchanged ETag avoids installation; a changed response installs full items, files, saved data, playlists and settings at [stores/library.ts:127](../../../../ui_web/src/stores/library.ts#L127). The delta implementation later in the file is the legacy manifest path, not the path used once `collectionItems` is non-null. [api.ts:683](../../../../ui_web/src/lib/api.ts#L683) confirms that canonical collection requests negotiate an ETag, not a delta.

**Read:** Installation preserves entities with keyed `reconcile`, but also calls [lib/media.ts:36](../../../../ui_web/src/lib/media.ts#L36), replacing a signal holding the whole artwork-metadata dictionary. Every reactive `coverUrl`/`artworkCandidates` read of that dictionary becomes eligible to recompute, even when only another song changed. [lib/media.ts:95](../../../../ui_web/src/lib/media.ts#L95) reads this shared signal; `bustCovers` separately changes the URL version for all covers. The global bust is sensibly limited by `cover_changed` at [stores/runtime.ts:482](../../../../ui_web/src/stores/runtime.ts#L482).

**Consequence inferred from code:** One accepted collection change still entails full payload parsing, reconciliation passes and potentially broad artwork computations. This can interrupt interaction when changes land during scrolling. It does not mean every DOM node changes or every image refetches: equality downstream and stable URLs can prevent those outcomes.

**Useful existing protections, read:** Library events coalesce over the code's 1,500 ms window; requests have single-flight and generation guards ([stores/library.ts:39](../../../../ui_web/src/stores/library.ts#L39), [103](../../../../ui_web/src/stores/library.ts#L103)). Download progress uses leaf-path writes rather than replacing the queue ([stores/downloads.ts:58](../../../../ui_web/src/stores/downloads.ts#L58)). Those should survive migration.

### 4. Collection changes can leave the catalog projection stale

**Read:** `installCollection` advances `collectionRevision` ([stores/library.ts:138](../../../../ui_web/src/stores/library.ts#L138)); `refreshCatalog` gates against the separate `revision` and `catalogRevision` ([stores/library.ts:143](../../../../ui_web/src/stores/library.ts#L143)). The canonical refresh branch never advances that manifest `revision`. After the initial catalog request succeeds, a subsequent changed collection can therefore skip catalog invalidation.

**Measured:** `catalog-refresh-probe.mjs` executes the actual `library.ts` controller after stripping types/imports, with an in-memory Solid store and stubbed REST/catalog ports. Run with `node --conditions=browser <output>/catalog-refresh-probe.mjs`. Node v26.13.1. Initial canonical load requested the catalog once; accepting a second collection with a changed ETag left the catalog-call count at one. The second request correctly sent the previous collection ETag. Assertions passed; `catalog-refresh-results.json` records the sequence.

**Concrete consequence inferred from consumers:** Song data can advance while catalog artists/album query revisions remain unchanged. [Library.tsx:63](../../../../ui_web/src/routes/Library.tsx#L63) and its album resource at line 71 consume those projections. A new download or remote change can therefore appear differently across views. This is a confirmed controller transition, not a reproduced end-to-end browser scenario. It demonstrates that state ownership contributes to inconsistency independently of styling.

### 5. Virtualization and scroll coordinates have multiple owners and incompatible lifecycle repairs

**Read:** Five components instantiate virtualizers: [VirtualRows.tsx:83](../../../../ui_web/src/components/VirtualRows.tsx#L83), [VirtualBrowseRows.tsx:13](../../../../ui_web/src/components/VirtualBrowseRows.tsx#L13), [TrackList.tsx:59](../../../../ui_web/src/components/TrackList.tsx#L59), [LibrarySearchResults.tsx:82](../../../../ui_web/src/components/LibrarySearchResults.tsx#L82), [ProgramQueue.tsx:30](../../../../ui_web/src/components/ProgramQueue.tsx#L30). They differ in viewport sizing, dynamic measurement, overscan, readiness, focus handling and identity.

**Read:** `VirtualRows` deliberately remounts its entire small `Rows` subtree once in the next animation frame to repair an initial viewport sampling problem ([VirtualRows.tsx:30](../../../../ui_web/src/components/VirtualRows.tsx#L30)). This is bounded window work, not a remount on every scroll, but it adds avoidable initial row/observer churn. Other implementations do not share that repair.

**Read:** The installed Solid adapter reconciles virtual descriptors by **index**, including when core item keys are supplied (adapter src/index.tsx:73 (`ui_web/node_modules/@tanstack/solid-virtual/src/index.tsx:73`)). `TrackList` correctly reads row data reactively instead of capturing the first occupant. `ProgramQueue` separately renders primitive occurrence keys through a positions map ([ProgramQueue.tsx:17](../../../../ui_web/src/components/ProgramQueue.tsx#L17)); `PlayerTrackList` preserves section/card identity with its own `KeyedItems` ([PlayerTrackList.tsx:389](../../../../ui_web/src/components/PlayerTrackList.tsx#L389)). Simply adding `getItemKey` everywhere does not itself make the adapter's `For` entity-keyed. Replacing every `For` with `Index` would also be wrong for moving, stateful rows.

**Read:** Origin handling diverges. [PodcastShow.tsx:148](../../../../ui_web/src/routes/PodcastShow.tsx#L148) measures its header and passes `scrollMargin`. [LibrarySearchResults.tsx:102](../../../../ui_web/src/components/LibrarySearchResults.tsx#L102) puts saved entities before the virtual canvas without accounting for their height in the virtualizer. The player browser likewise puts a toolbar and optional filter before lists without passing `scrollMargin` ([NowPlayingBrowser.tsx:898](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L898), [1153](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L1153)).

**Consequence inferred from code:** Overscan is masking some origin mismatch; if preceding content exceeds its allowance, visible early rows can be outside the mounted range. Stateful focus/edit/press ownership also follows different rules across implementations. These are geometry and identity hazards, not a measured frequency of blank rows. Central infrastructure needs an explicit header origin, readiness and identity contract rather than another per-screen workaround.

### 6. View visibility and reactive lifetime are different, but only partly modeled

**Read:** The app shell persists, and ordinary route components are reconstructed rather than kept alive: [app.tsx:26](../../../../ui_web/src/app.tsx#L26), [AuthenticatedPlayer.tsx:43](../../../../ui_web/src/AuthenticatedPlayer.tsx#L43), [AsyncPage.tsx:10](../../../../ui_web/src/components/AsyncPage.tsx#L10). `asyncPage` caches code, not mounted pages. Browser/tab restoration stores locations and pixel offsets, not route DOM ([tabMemory.ts:17](../../../../ui_web/src/lib/tabMemory.ts#L17), [scrollHistory.tsx:31](../../../../ui_web/src/lib/scrollHistory.tsx#L31)). HashRouter itself is not performing list work on ordinary wheel events.

**Read:** The fullscreen player has a different lifetime. `opened` latches true after first opening ([PlayerSurface.tsx:57](../../../../ui_web/src/components/PlayerSurface.tsx#L57)); NORMAL remains mounted afterward ([481](../../../../ui_web/src/components/PlayerSurface.tsx#L481)). Auto mounts while its mode is active. All mobile workspace panels are mounted and inactive panels become inert ([PlayerWorkspace.tsx:69](../../../../ui_web/src/components/PlayerWorkspace.tsx#L69), [404](../../../../ui_web/src/components/PlayerWorkspace.tsx#L404)). CSS visibility and inert prevent rendering/access, but do not dispose reactive owners.

**Read:** The browser's remote searches are activity-gated; its whole-library sorting, favourite/artist projections and identity map are not ([NowPlayingBrowser.tsx:213](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L213), [250](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L250), [496](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L496)). NORMAL passes surface visibility, not mobile-panel visibility, as browser activity ([NowPlaying.tsx:375](../../../../ui_web/src/components/NowPlaying.tsx#L375)).

**Read:** Progress presentation already has a useful explicit boundary: [PlayerStage.tsx:97](../../../../ui_web/src/components/PlayerStage.tsx#L97) unsubscribes from clock reads when hidden/closed using `untrack`. Lyrics gate on document visibility, rather than a supplied surface-activity contract, and can run a 420 ms scroll tween when following a new line ([LyricsPanelView.tsx:138](../../../../ui_web/src/components/LyricsPanelView.tsx#L138), [169](../../../../ui_web/src/components/LyricsPanelView.tsx#L169)). The native program transport separately maintains a 500 ms presentation timer ([ProgramTransport.tsx:12](../../../../ui_web/src/components/ProgramTransport.tsx#L12)).

**Consequence inferred from code:** After using the player, collection/preference changes can drive both the foreground route and retained player projections. Open but offscreen mobile panels also remain eligible for work. Keep worthwhile state retention, but distinguish mounted, visible, interactive and transport-active. Do not tie audio scheduling to presentation visibility.

### 7. Scroll work is mostly local, but restoration, geometry and gesture policies remain scattered

**Read:** Route scroll history writes two plain maps per scroll and cancels restoration on input ([scrollHistory.tsx:218](../../../../ui_web/src/lib/scrollHistory.tsx#L218)). The player browser instead replaces its global navigation-frame signal on every captured body scroll ([NowPlayingBrowser.tsx:589](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L589), [musicBrowserNavigation.ts:29](../../../../ui_web/src/lib/musicBrowserNavigation.ts#L29)). Its separate restoration engine observes subtree mutations and retries layout-dependent offsets within a 1,500 ms grace period ([NowPlayingBrowser.tsx:505](../../../../ui_web/src/components/NowPlayingBrowser.tsx#L505)).

**Measured:** In the rerun probe, 100 scroll-frame writes evaluated the `currentView` memo 100 times but generated **zero** downstream view notifications. This is small upstream allocation/fan-out, not proof that scrolling reruns the whole browser tree.

**Read:** AppBar batches its geometry read into one rAF ([AppBar.tsx:49](../../../../ui_web/src/components/AppBar.tsx#L49)). The mobile carousel repeatedly queries tiles and reads rectangles for progress ([PlayerWorkspace.tsx:89](../../../../ui_web/src/components/PlayerWorkspace.tsx#L89), [167](../../../../ui_web/src/components/PlayerWorkspace.tsx#L167)). Rail overflow markers read scroll dimensions; these are not all continuous loops ([SearchDiscoveryView.tsx:95](../../../../ui_web/src/components/SearchDiscoveryView.tsx#L95)). Drag edge scrolling is a rAF loop only while dragging, with cleanup ([PlayerTrackList.tsx:200](../../../../ui_web/src/components/PlayerTrackList.tsx#L200)). No IntersectionObserver is used in the inspected UI source. Responsive taps cancel on a pan and do not read layout on each pointer move ([responsiveTap.ts:103](../../../../ui_web/src/lib/responsiveTap.ts#L103)). Library, overlay and player-dismiss gestures nevertheless each maintain additional touch handling and non-passive listeners.

**Consequence inferred from code:** Several policies can respond to the same gesture/layout transition. This increases compatibility and testing burden. A layout read is not automatically a forced layout; an actual trace must establish that preceding writes made it expensive. Preserve native kinetic scroll and the existing gesture-cancellation protections while consolidating ownership.

### 8. Visual consistency is limited by duplicated compositions and image paths, not by CSS Modules

**Read:** Desktop `SongRow` and mobile `MusicListRowView` are separate DOM compositions selected in [SongRow.tsx:115](../../../../ui_web/src/components/SongRow.tsx#L115). There are additional catalog/search/player rows and independently styled album/artist/discovery cards. Mobile consolidation is real, but [MusicListRowView.tsx:96](../../../../ui_web/src/components/MusicListRowView.tsx#L96) is not yet a universal desktop-and-mobile presentation contract.

**Read:** Rows usually use CSS background artwork ([lib/cover.ts:24](../../../../ui_web/src/lib/cover.ts#L24)); grids use [CoverImage.tsx:12](../../../../ui_web/src/components/CoverImage.tsx#L12). `CoverImage` supplies srcset, size selection, lazy loading, fallback handling and a bounded painted-URL hint, but creates its own ResizeObserver and initial rectangle read per mounted image. Background-image rows use a different decode/loading path. The row URLs are usually thumbnail-sized, so it would be inaccurate to claim all rows fetch full originals.

**Read:** Tokens provide typography, density, palette, motion and stacking scales ([tokens.css:155](../../../../ui_web/src/styles/tokens.css#L155)); modules scope most composition. Globals implement reset, primary-scroll and playback-state conventions ([app.css:1](../../../../ui_web/src/styles/app.css#L1), [201](../../../../ui_web/src/styles/app.css#L201), [246](../../../../ui_web/src/styles/app.css#L246)). `:has()` is used for shell clearance and local focus treatment, not evidence by itself of slow selector matching. A search found no explicit `contain` or `content-visibility` declarations; container sizing elsewhere is a separate mechanism. Their absence does not prove that blanket containment would help.

**Read:** Compositing boundaries are deliberate but application-specific: the player is a body portal with isolation, a filtered artwork backdrop and local stacking ([PlayerSurface.module.css:23](../../../../ui_web/src/components/PlayerSurface.module.css#L23), [111](../../../../ui_web/src/components/PlayerSurface.module.css#L111)); the shell is hidden after opening ([app.css:95](../../../../ui_web/src/styles/app.css#L95)); the floating mini-player and overlay scrims retain backdrop filters. The overlay registry, cursor-menu outlet and player portal have separate owners, though top-level z-tokens coordinate them ([overlay.tsx:329](../../../../ui_web/src/lib/overlay.tsx#L329), [contextMenu.tsx:40](../../../../ui_web/src/lib/contextMenu.tsx#L40)). Local z-values inside an isolated surface are not automatically stacking bugs.

**Consequence inferred from code:** Tokens alone cannot keep row semantics, visual states, card geometry, artwork behavior or gestures cohesive when compositions remain separate. CSS effects also retain raster/compositor costs that changing JavaScript frameworks would not remove. No selector, blur or image-decode cost was measured here.

### 9. Existing splitting and tests protect behavior, but do not establish scrolling performance

**Read:** Authentication and most routes already load asynchronously ([main.tsx:83](../../../../ui_web/src/main.tsx#L83), [AuthenticatedPlayer.tsx:6](../../../../ui_web/src/AuthenticatedPlayer.tsx#L6)). This is a startup/reliability tradeoff, not evidence of a monolithic unsplit SPA.

**Measured:** `bundle-inspection.json` inspects the supplied production manifest and sums unique static JS dependencies per entry: HTML entry 135,304 bytes; authenticated entry 510,280 bytes; player-views entry 708,877 bytes. The sets overlap and **must not be added**. CSS, dynamic descendants, transfer headers and parse/execute time are excluded. This is disk inspection, not observed loading or evidence of frame stalls. No build was run.

**Read:** [VirtualRows.test.tsx:38](../../../../ui_web/src/components/VirtualRows.test.tsx#L38) asserts bounded mounting and geometry with fabricated jsdom dimensions. Browser profiles cover Chromium/WebKit mobile/desktop; their default is reduced motion ([playwright.config.ts:34](../../../../ui_web/playwright.config.ts#L34)). Dedicated rendering tests override that default and check effects/lifecycle policy ([player-rendering.spec.ts:4](../../../../ui_web/tests/browser/player-rendering.spec.ts#L4)). Geometry, interaction, scroll restoration, token and module-boundary tests exist. This is substantive coverage, not an absence of tests.

**Read:** A commonly reused music fixture provides 320 tracks, closes sockets and uses the legacy library shape ([music-browser-fixture.ts:4](../../../../ui_web/tests/browser/music-browser-fixture.ts#L4)). It cannot exercise the canonical ETag/catalog transition reproduced above. Frame appearance or DOM bounds also do not measure sustained native scroll latency.

**Consequence:** A green functional suite can coexist with collection-size-sensitive work, long tasks, cold artwork stalls and device-specific compositing defects. Architectural invariants and representative production traces need separate evidence channels.

## What the reactive/data-flow review rules out, and what it retains

**Read + measured:** A single `createStore` is not a whole-app broadcast. The store is proxy/path reactive ([stores/core.ts:281](../../../../ui_web/src/stores/core.ts#L281)). Playback time is written to a leaf ([stores/runtime.ts:351](../../../../ui_web/src/stores/runtime.ts#L351)); saved/playing identities do not read that clock. The probe produced zero saved-lookup reruns on a clock update and zero extra `mapArray` mounts when 30 keyed store entities were reconciled. That experiment verifies the underlying pattern, not every component's lifetime.

**Read:** Playing/queued identity sets can still notify their mounted subscribers on a track/queue change ([stores/identity.ts:52](../../../../ui_web/src/stores/identity.ts#L52)). Shared requested-row selection is another broad boolean derivation ([MusicListRowView.tsx:11](../../../../ui_web/src/components/MusicListRowView.tsx#L11)). These are candidates for keyed selectors, but their update frequency is different from the playback clock. Preferences intentionally change geometry/theme globally; `createRowHeight` remeasures on interface-size changes, not continuously on scroll ([rowHeight.ts:6](../../../../ui_web/src/lib/rowHeight.ts#L6)).

**Read:** Transport time events also perform progress/learning/runway work; changing the DOM framework would not remove this service work. Socket events enter guarded controllers, update narrow download fields or schedule collection synchronization. REST snapshots reconcile entities before projections feed views. Retain that separation and the account-lifetime teardown ([stores/index.ts:23](../../../../ui_web/src/stores/index.ts#L23), [608](../../../../ui_web/src/stores/index.ts#L608)). The store split is valuable even though its selectors and projection ownership need repair.

## Upstream comparison

All sources below were accessed on 2026-11-16. These are design/API comparisons, not claims that another application reaches a particular frame rate on this hardware.

- **Sourced — Solid:** [fine-grained reactivity](https://docs.solidjs.com/advanced-concepts/fine-grained-reactivity), [list rendering](https://docs.solidjs.com/concepts/control-flow/list-rendering), [reconcile](https://docs.solidjs.com/reference/store-utilities/reconcile). Track actual property reads; use `For` for changing item identity/order and `Index` for stable positional slots; reconcile incoming snapshots with the relevant identity. The current proxy store, keyed snapshot installation and accessor-based virtual slots align with these principles. Broad scans and array replacement can still create broad dependency work within that model.
- **Sourced — Solid:** [createSelector](https://docs.solidjs.com/reference/secondary-primitives/create-selector) keeps boolean subscriptions keyed by the compared value. Apply it, or keyed leaf state, to selection/playback membership where appropriate; preserve multi-identity and ambiguity semantics rather than replacing them with a naïve track-ID comparison.
- **Sourced — TanStack Virtual:** [Virtualizer API](https://tanstack.com/virtual/latest/docs/api/virtualizer) documents explicit scroll elements, estimates, dynamic measurement, stable item keys and scroll margins. A preceding header belongs in the origin model; measured rows require reliable size-cache identity. The installed Solid adapter's index reconciliation must also be accounted for. Current online documentation includes APIs that may postdate the installed version; the recommendation does not depend on newer anchoring features.
- **Sourced — mature Solid library code, Kobalte:** [selectable-collection implementation](https://raw.githubusercontent.com/kobaltedev/kobalte/main/packages/core/src/selection/create-selectable-collection.ts) separates selection/keyboard delegates, collection references, virtualized behavior and `scrollToKey`. That supports treating focus and logical item identity as collection infrastructure, not miscellaneous row effects. [Kobalte styling](https://kobalte.dev/docs/core/overview/styling) exposes state through component parts and data attributes while leaving visual styling to the app. CSS Modules remain compatible.
- **Sourced — mature Solid library code, Corvu:** [drawer Root](https://raw.githubusercontent.com/corvudev/corvu/main/packages/drawer/src/Root.tsx), [drawer Content](https://raw.githubusercontent.com/corvudev/corvu/main/packages/drawer/src/Content.tsx), [drawer documentation](https://corvu.dev/docs/primitives/drawer/). Drawer behavior composes over dialog behavior, exposes transition state, and installs/removes gesture listeners with open state. This is a useful model for common overlay lifecycle and scroll arbitration. It is not proof that adopting the package would preserve this app's gestures without compatibility tests.

Kobalte and Corvu were inspected as mature Solid infrastructure examples, not benchmarked application substitutes. Attempts to retrieve an OpenCode application file returned 404/403; no architecture claim here relies on that unavailable file.

## Open questions and what would settle them

1. **Which task freezes the actual song scroll?** The source cannot allocate causality between saved lookups, layout, artwork decoding, GC and compositing. A short production trace on the exact failing surface with native input, warm and cold images, current saved count, and accepted-event timestamps would settle it. Repeat on the X270 when accessible; desktop CPU throttling is not a replacement for its GPU/memory behavior.
2. **How much does saved lookup matter in the owner's library?** Record the saved count, identities used, actual per-new-row selector calls and their time. The synthetic near-end workload establishes scaling, not prevalence or elapsed cost.
3. **How many full snapshots and projection updates arrive while scrolling?** A fixture with canonical ETags, source/mark edits and socket bursts should log response bytes, accepted revisions and derivation counts. Existing legacy/socket-disabled fixtures leave this transition underrepresented.
4. **What is the intended anchor after prepend/filter/reorder?** Decide whether to preserve the visible item or a literal pixel offset per interaction; test both list content and focus against that decision. Current infrastructure does not expose one cross-surface policy.
5. **Which retained panels are worth their background cost?** Count retained roots, listeners, observers and presentation work before first player open, after close, in Auto and during navigation. Preserve lightweight view snapshots and cached data; retain full DOM only where measured reopen benefit warrants it.
6. **Which materials actually differ across supported WebViews?** The existing glass test documents known rendering limitations but does not reproduce them here. Inspect rendered Chromium, WebKit and Windows WebView2/native Android compositions with the same content. CSS support detection alone cannot establish the painted result.
7. **Do device differences require new rendering technology?** There is no source evidence for that conclusion. Only if the consolidated, bounded DOM architecture still cannot meet refresh-derived frame deadlines with trace-identified costs removed should a competing renderer/framework be prototyped against the same feature-complete fixture.

## Concrete target architecture and shippable migration order

The target is a **Solid application with enforced ownership and bounded presentation**, using the existing engine contracts and platform adapters.

### Layers and ownership

1. **Platform ports:** REST/socket/session transport, browser audio/Media Session, native program commands, platform lifecycle and appearance. Browser/PWA and Windows share the browser player; Android supplies native controllers to shared Solid views; the SwiftUI iOS client remains separate. This matches the boundary documented in [android/HANDOFF.md:19](../../../../docs/internal/android/HANDOFF.md#L19) and the separate entry in [mobile/main.tsx:1](../../../../ui_web/src/mobile/main.tsx#L1). Shared presentation must not import web audio/store controllers.
2. **Account-scoped domain state:** keyed musical entities, keyed per-item saved/favourite/download state and ordered ID vectors; separate occurrence-keyed queue state; explicit revisions for accepted data and dependent catalog projections. Compatibility aliases resolve centrally without merging ambiguous musical entities. Transport clocks and scheduling are service state, independent of route/panel visibility. Existing `state/actions` can remain a compatibility facade during migration.
3. **Query/projection layer:** one owner for browse order, normalized search/indexes and catalog query caches. Keys include account/storage and the actual query/filter/sort inputs; invalidation follows accepted collection revisions. Cache data, not arbitrary mounted route trees. Share projections only when semantics match: downloaded-only, all music and favourites are distinct queries.
4. **Feature controllers and navigation:** routes/panels translate intent to domain commands and compose query projections. URL/shareable state stays in routing; session-only player stacks and expansion/edit state use lightweight keyed snapshots. Pixel scroll samples live beside the owning scroller, outside broad reactive navigation signals. Persist a logical anchor plus intra-item offset when identity preservation is required.
5. **Collection/scroll infrastructure:** one registered vertical scroll owner per route or intentionally independent panel/lane, with an explicit horizontal pager contract. One virtual-list/grid host owns viewport readiness, origin/header extent, measurements, stable size keys, DOM identity policy, focus pinning and restore cancellation. Fixed rows consume the density tokens; genuinely variable rows are measured. Virtual slots may recycle only with explicit state reset/ownership rules. Stateful rows follow item/occurrence keys independently of the installed adapter's index slots. Grid column changes rebuild row geometry, not the entire collection DOM. Rails with deliberately small supplied data stay simple.
6. **Presentation and styling:** pure semantic row/card/toolbar/header/menu/artwork parts with browser/native adapters. Desktop and mobile may arrange parts differently, but use the same state vocabulary and action contracts. Tokens own density, color, typography, motion, stacking and material recipes; modules own component geometry; globals are limited to reset and documented shell conventions. Overlay layers share stack/focus/dismissal policy while allowing distinct portal surfaces. Region-local visibility suspends presentation observers/derivations; audio remains active. Effects and containment are approved per region through trace and visual evidence.
